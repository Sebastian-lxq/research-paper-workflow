# Feedback, decisions and research continuity

Use this for accumulated comments, changed research direction or cross-stage
resumption. A local sentence edit does not require a new feedback database.

## Record once in the existing project

Find the project's revision notes, author locks, mentor feedback log or equivalent
store first. Map these concepts to its existing fields; they are not a new machine
schema. If there is no suitable record and persistence is within scope, adapt
[feedback-index.md](../assets/feedback-index.md) beside the project notes.

Keep the original statement or a faithful short extract with message/date/source
locator. Use source kinds that distinguish direct user requests, user-relayed
mentor advice, publications and AI review. A relayed comment can guide the task
without becoming verified direct communication, a mentor's enduring preference,
or a rule for other projects. Do not copy private quotations into global skills.

Separate decision (pending/adopted/rejected/deferred with reasons), allowed action
(collect only, plan, or implement within the existing scope), and implementation
(not started, changed, checked). These labels describe evidence; the actor must
read the actual user instruction to establish authorization. Silence, an AI vote
or a populated field does not create it. Ordinary adopted suggestions need no
new supervisor gate. If a formal supervisor finding exists, reference its ID and
let its existing finding-specific verification own closure.

For each actionable item, record the affected object/version, intended change,
implementation locator, relevant acceptance check and remaining dependencies.
"The plan addresses it" is not "the algorithm/experiment/manuscript implements
it". Rejected or deferred suggestions retain their reasons and any revisit
condition. An unchanged file can be the correct outcome of an evidence-backed
rejection; never manufacture edits to make a suggestions table look complete.

When the user says collect now and revise later, keep manuscript/code unchanged.
If they authorize keeping notes, record comments there; if the request is fully
read-only, return the index in the conversation without writing project state.
Later implementation uses that history without asking for the same authorization
again. New material choices still follow the user's actual scope.

## Apply a research-direction change

Resolve ambiguous roles before changing the theory: what is the target parameter,
nuisance estimator, learned aggregation rule and calibration procedure? Generalizing
one is not generalizing all of them. Record the new maintained model, estimand or
null, identification assumptions, alternatives and non-goals alongside the old
decision it supersedes. Preserve disagreements and proof boundaries.

Trace the actual dependencies: title/abstract/introduction, definitions and proofs,
algorithm, design/config/results, literature positioning, meeting briefs and
roundtable recommendations. Revalidate reusable evidence under the new object.
Mark a related artifact outside the authorized edit scope as historical or pending
in the current notes, rather than editing it unasked or consuming it as current.
Do not rewrite the old discussion as if it had reached the new decision.

Use the existing writer semantic-change protocol and workflow track rules when
the research scope materially changes. A single formatting preference does not
require a new track. Never reactivate superseded guidance just because a retrieved
old roundtable was long or confident.

## Resume with a short derived summary

Before substantive continuation, recover current target/method, active artifacts,
supported claims and limits, recent decisions with provenance, unfinished accepted
comments and next action. Generate a compact summary only where it helps handoff;
link to the authoritative records and state the version/date. Refresh affected
parts after a real change; do not re-read all papers or restart passed stages.

Keep actual task completion, scientific support and external submission permission
separate. A short summary is navigation to evidence, not evidence that a proof or
experiment has been completed.

For repeatable generation from explicitly mapped existing fields, use
[resume-view.md](resume-view.md). Keep changes to the source feedback/decision
record once; rebuild the derived view after meaningful updates. During an issue,
retain its original problem, target, preserved content, actual change, check
result and retain/rework reason in that existing record. Do not repeat unchanged
sections or fill unavailable time/cost measures with zero.
